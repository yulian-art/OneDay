# core-media

录制与媒体的**基础设施层**：时间映射、分片合并、MediaCodec 解码。

这一层刻意**不依赖 Insta360 SDK**。原因有两个：

1. 方案文档把「预览稳定获取」「跨时钟对应」列为最难的两个环节。这些逻辑
   必须能脱离真机、用单元测试穷举验证，否则出了问题只能靠真机碰运气。
2. 相机机型/固件可能更换，但「一帧分多次回调」「两个时钟有漂移」这两件事
   不会变。抽象掉 SDK 之后，这套逻辑可以直接复用到别的相机。

---

## 1. 时间映射（`time/`）

### 问题

方案文档「08 整个流程最难的八个环节」第 2 条：

> 跨时钟对应 —— 按钮、手机、预览、原片时间不同
> 保存原始时间，以可见同步事件建立映射
> 若用线性映射，应测偏移与漂移；停录、重启、分段分别处理
> 时间同步不能用模型猜：接收时间不等于按下时间，命令发出不等于第一帧时间

### 设计

| 类型 | 作用 |
|---|---|
| `ClockDomain` | 六个时钟域的显式枚举。任何跨域换算都必须经过 `RecordingTimeline`，**禁止直接相减**。 |
| `AnchorSource` | 证据强度分级。可见同步事件权重 4.0，「帧接收」只有 1.0 —— 弱证据不会淹没强证据。 |
| `LinearTimeMap` | 带权最小二乘拟合 `reference = intercept + raw × scale`。漂移以 ppm 暴露，供验收直接读数。 |
| `RecordingTimeline` | 管理多个 `TimeSegment`，把任意域换算到原片域。 |

> 同步事件用 `SyncMarker` 表示，直接挂在 `RecordingTimeline` 的片段上；
> 早期版本的 `SyncMarkerLog` 类从未被使用，已删除。

### 三个关键决定

**① 用仿射而不是纯偏移。**
两个晶振不可能一致。纯偏移在长会话下会累积到秒级误差。所以同时拟合偏移与
漂移（`scale`），并用 `driftPpm` 暴露出来 —— 文档要求「测偏移与漂移」，
这个数字就是那条验收项的直接产出。

**② 用小规模 RANSAC 而不是普通最小二乘。**
这是被单元测试逼出来的修正。最初用带权最小二乘，测试 `weak evidence is outvoted`
失败：一个配错的锚点（比如同步事件被误检）会把整条斜率拽歪，
后续所有跳转全错。锚点本来就少，普通最小二乘的崩溃点太低。

现在的做法：由每对锚点生成候选斜率 → 对每个候选斜率用「截距中位数」统计内点 →
取内点最多的模型 → 只在内点上做最小二乘。被排除的锚点记入 `rejectedAnchors`，
并拉低置信度，因为「有锚点对不上」本身就需要人看一眼。

**③ 外推如实降级，不假装精确。**
换算结果不是裸 `Long`，而是 `TimeMappingResult`：带置信度、误差上界、
外推距离。超过 5 秒的外推直接降为 `UNCERTAIN`。锚点为空时 `fit()` 返回 null ——
文档说「不能用模型猜」，没有证据就不该伪造一个映射。

### 分段的理由

每次停录再开录都会新建一个原片文件，**原片时间轴重新从 0 开始**。
若把整场会话当成一条时间轴，第二段之后的事件全会跳错位置。
所以每段持有自己的 `LinearTimeMap`，段间不做插值。

### 两步完成的同步事件

真实流程里，用户拍手那一刻我们只可能拿到**手机时刻**与**预览流时间戳**；
这次拍手在**原片**里的位置，要等分析链路在原片中看到它才知道。
所以映射分两步成立：

```kotlin
timeline.recordSyncMarker(SyncMarker("s1", "clap", mapOf(
    ClockDomain.PHONE_MONOTONIC to 2_000L,
    ClockDomain.PREVIEW_STREAM  to 50_000L,
)))
// 此时 preview→original 还不成立，toOriginal() 返回 null

timeline.completeSyncMarker("s1", ClockDomain.ORIGINAL_FILE, 7_000L)
// 补齐后映射成立
```

界面上把这个状态如实显示为「已打点 N 次，其中 M 次尚未定位到原片」，
而不是假装打点立刻生效。

## 2. 分片合并（`stream/`）

方案文档「05」点名的失败模式：

> 一个编码帧可能分多次回调，应按同一时间戳合并分片；
> 错误地把单独分片送入解码器可能造成绿屏或坏帧

`FrameAssembler` 就是这一层的实现。核心规则（按 `MediaStreamType` 分组）：

| 情况 | 处理 |
|---|---|
| 时间戳相同 | 继续累积到当前待定帧 |
| 时间戳更大 | 当前帧确认收完 → 发出 → 为新时间戳开新帧 |
| 时间戳更小 | 迟到分片，结构上无法再并入，计入 `outOfOrderFragments` |

**「帧完整」是靠「下一帧时间戳出现」推断的**，所以流一停就永远等不到最后一帧。
`flushStale(nowUs)` 解决这个问题（默认 250ms 超时），代价是迟到分片会被记为乱序。
没有它，每一段的最后一帧都会丢。

`StreamStats` 里的 `avgFragmentsPerFrame` 是**验证「相机是否真的在分片」的证据**：
如果这个数字 > 1，就说明合并层不是多余的。

### 一个要说清楚的不变式：待定帧恒 ≤1

入队只发生在两处 —— 「队列为空时入队」与「先 `removeLast` 再入队」——
所以每个流类型的待定队列长度**恒为 0 或 1**。

这意味着两件事：

- **本层不需要背压**，因为它从不积压。有界队列与丢整帧策略在
  [解码准入](#3-解码准入codecdecoderadmissionpolicy) 那一层。
- 这里**不会**因为「队列溢出」丢帧。早期版本有一个 `maxPendingFrames`
  配置项与对应分支声称做这件事，但它对任何 ≥1 的取值都不可达，
  取 0 时又会丢掉刚入队的最新帧（与注释写的「丢最旧的」相反）——
  属于假保证，已连同配置项一起删除。

## 3. 解码准入（`codec/DecoderAdmissionPolicy`）

方案文档「08」第 1 条：

> 独立解码、有界队列；不能随意丢编码分片

区别在于**丢什么**：

- 丢**分片** → 拼出残废帧 → 绿屏/坏帧，绝对禁止；
- 丢**整帧** → 合法，但 H.264/H.265 有帧间预测，丢一帧会让后续 P/B 帧
  失去参考，**必须等到下一个关键帧**才能恢复。

所以策略是：队列满 → 丢队首整帧 → 置 `needsKeyframe = true` →
丢弃所有非关键帧直到关键帧到来。画面会「卡一下再恢复」，而不是「一路花屏到底」。

这个类不依赖 Android，可以在 JVM 上穷举验证（见 `DecoderAdmissionPolicyTest`）。

## 4. 编码格式探测（`codec/VideoCodecFormat`）

文档：「编码格式也需按实际机型、固件判断」。所以不写死 H.264，
而是从码流里认：

| | NAL 头 | SPS | PPS | VPS | IDR |
|---|---|---|---|---|---|
| H.264 | 1 字节，`b0 & 0x1F` | 7 | 8 | — | 5 |
| H.265 | 2 字节，`(b0>>1) & 0x3F` | 33 | 34 | **32** | 19/20 |

对同一段字节按两种解释分别打分，取分高者。**VPS 只有 HEVC 才有**，
所以出现 VPS 时直接判定 HEVC（置信度 0.99）。

`decide()` 支持多帧投票 —— 单帧不足为凭，上层应喂若干帧再定。

## 5. `FrameDecoder`

MediaCodec 异步封装。职责边界刻意收窄，只做三件事：

1. 用 `DecoderAdmissionPolicy` 做有界准入；
2. 把完整编码帧喂给 MediaCodec；
3. 把 `presentationTimeUs` **原样**回调出去。

第 3 点很重要：时间戳在这里被改写，预览→原片的映射就断了。
所以解码器只是一个透传管道，不做任何时间加工。

属于**分析链路**，因此任何异常都被吞掉并上报 `DecodeListener.onDecodeError`，
绝不向上抛到录制流程。

## 测试

```
./gradlew :core-media:test
```

覆盖：

- `LinearTimeMapTest` —— 偏移/漂移/离群拒绝/外推降级/加权
- `RecordingTimelineTest` —— 分段独立、两步同步事件、弱兜底、反查
- `FrameAssemblerTest` —— 同时间戳合并、乱序、超时 flush、上限保护、统计
- `DecoderAdmissionPolicyTest` —— 整帧驱逐、关键帧重同步、FIFO
- `VideoCodecFormatTest` —— H.264/H.265 判别、起始码/长度前缀、多帧投票

所有测试都是纯 JVM，不需要真机或模拟器。
